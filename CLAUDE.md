# emporiad — notes for agents

Prometheus exporter for Emporia Vue energy monitors, running on bigthink (Hugh's NixOS server). Siblings: `../kasad`, `../comfortd`, `../breezyd`. Follow their conventions.

## Hard rules

- **This repo is public.** No circuit names, site names, device ids, emails or account details in commits. Test fixtures are invented. Keep names out of `grafana/emporiad.json`. The only screenshot is `docs/screenshots/grafana.png`, taken from a temporary copy of the dashboard that relabels circuits `Circuit N` (label_replace on channel_num); check any new one for circuit, site and device names before committing.
- **The Emporia login** (email, then password) is `/persist/emporiad/credentials` on bigthink (root-only, on the persisted btrfs, passed in with LoadCredential); there is no copy on the Mac. For a local run, ask Hugh for a temporary file and delete it afterwards. Never print, log or commit it.
- Read-only: emporiad only GETs. Emporia's API can also switch smart plugs and EV chargers; don't add writes without Hugh agreeing.
- Dependencies: `prometheus/client_golang` only (`google.golang.org/protobuf`'s protowire, which client_golang already brings, is used directly for remote write). Ask before adding more. After a go.mod change, recompute `vendorHash` (set `pkgs.lib.fakeHash`, `just gate`, paste the `got:` hash).

## Layout

- `internal/cognito`: USER_SRP_AUTH and REFRESH_TOKEN_AUTH against Cognito's JSON API. The test's fake pool does the server half of SRP, so maths mistakes fail there.
- `internal/emporia`: `Session` (token cache, refresh, re-login), `Client` (`customers/devices`, `getChartUsage` per channel per minute, `getDeviceListUsages` per hour).
- `internal/promwrite`: remote write 1.0 by hand (protowire, literal-only snappy), named targets (`--push name=url`), per-target queues, and a "newest sample" query, so a restart resumes where each target's data ends. The package is identical in all four daemons (SPDX header aside); change the copies together.
- `internal/exporter`: poll loop (every 15m: one fetch from the furthest-behind target, at most 12h; each target is sent what it lacks; a target whose write failed is un-resumed (asked again where its data ends) and fetched for apart until it catches up, so it cannot pin the window; then finished hours (the newest first, for the targets level with it, then each target's own hours oldest first with the rest of the 12-hour budget, so a target far behind cannot hold the newest back); then one week of Emporia's hourly history, walking back from each target's oldest hour until a week is empty; after an outage a hole in the target's hourly series is found at resume from the store (`RunStart`, `NewestHourlyBefore`), so a restart mid-walk carries on from the newest run's start and then jumps to the old data) and the `/metrics` collector (newest sample of each pushed series with its timestamp and `pushed_<target>="true"`, health, device facts). `cmd/emporiad`: flags. `nix/module.nix`: the NixOS module (pushes to the local VictoriaMetrics, else Prometheus, and registers its scrape job with a drop rule for `pushed_<host>`; for Prometheus it asserts the receiver flag, which the host sets once).
- `internal/weather`: optional outdoor temperature from Open-Meteo (archive API for more than a week back, forecast API's past days after). `pollWeather` sends each target the hours after its newest `weather_temperature_celsius` (asked at resume; a year back if none), apart from the energy data's health. Hugh's location is only in his private NixOS config: never in this repo, tests use invented places.
- `grafana/emporiad.json`: importable dashboard; `internal/exporter/dashboard_test.go` fails if it uses a metric that is neither served nor in `exporter.Pushed`.

## Things learned

- RespondToAuthChallenge rejects an empty `Session`; Emporia's pool does not issue one, so leave the field out.
- `getDeviceListUsages` at `scale=1MIN` answers on a two-minute grid whose phase moves: on 2026-11-19 it gave odd minutes in the morning (16:00Z asked gave 15:59) and even ones by afternoon (16:43 gave 16:42). Polling it every minute lost half the minutes. Never use it per minute; at `1H` it gives the hour containing `instant`, unfinished if current.
- `getChartUsage` (one `channel` per call; a comma list returns the sum) gives every minute, final once returned, about a week back (all of 7 days ago was there on 2026-11-19). One call may span at most 13h20m at `1MIN` (HTTP 400 "larger than the allowed limit of PT13H20M"), so a backfill takes 12h a poll. Its bucket for the minute containing `end` is wrong (low), so ask one minute past what you want and drop it. It only returns completed minutes, but its newest one for mains (`1,2,3`) can read low: from 2026-11-19 22:29Z every poll's newest mains minute was two thirds of the circuits' sum while the circuits, fetched seconds later, were right; minutes before it were right. So a minute is ready only once the minute after it is filled too (the newest waits a poll and is read again). `1,2,3` cannot be split: on a Vue with an expansion, channels 1, 2 and 3 of the shared gid are circuits. It has no `Balance` (400): Balance is mains minus every circuit, which matched Emporia's own to 4 decimals.
- Prometheus (remote write, no out-of-order window) refuses samples older than about an hour, and one refused sample fails the whole request; the NixOS Prometheus module cannot set `out_of_order_time_window` (a `storage:` key with no flag). That is why bigthink moved to VictoriaMetrics, which takes any sample inside retention. Still never send a target older than the newest it holds, so a Prometheus target keeps working.
- Pull and push together: `/metrics` keeps every reading for any scraper. The `pushed_<name>` label lets a target's own scrape drop its copies; don't take readings off `/metrics` to avoid duplicates.
- 240 V circuits have `channelMultiplier: 2` (set in the app), and usage replies already include it: Emporia's own Balance equals mains minus the returned circuit values. Don't multiply again.
- `getChartUsage` at `scale=1H` spans at most 800 h a call ("PT800H"), at `1D` 12000 h; `1MIN` 13h20m. Hourly history goes back to the monitor's install (minutes: a week). 1H buckets are labelled by their start hour, an unaligned start snaps down, and unlike 1MIN the bucket at `end` is right (the current hour comes back unfinished). 1H in kWh and in Dollars equals `getDeviceListUsages` at 1H for the same hour.
- `energyUnit=Dollars` prices usage with the app's rate plan (`utilityRateGid` in locationProperties; the plan itself is not readable through the API). Checked against a year of the utility's bills: it matches the tariff per kWh except an optional per-kWh program charge, and moves between tiers by the app's billing-cycle start day. Hugh chose not to add fixed charges or optional programs.
- `/v1/...` endpoints take `Authorization: Bearer <id token>`, not `authtoken`; this account has no v1 sites.
- The circuit expansion (WAT001) has the same deviceGid as its Vue: they are one monitor. Usage replies list every channel, mains included, under that gid with the WAT001. So `Device.Parent` can equal `Device.Gid`; anything walking parents must stop at a repeat (it once spun forever).
- Finding a hole in an hourly series: `(timestamp(X) unless X offset 1h)[5y:1h]` is evaluated at the samples that have no sample an hour before (run starts). `timestamp()` of an `offset` selector gives the sample's own time on VictoriaMetrics, so avoid relying on it; to get the sample below a hole, ask `NewestHourlyBefore` (instant query with `time=`) instead. A 5y subquery at a 1h step is accepted and quick there.
